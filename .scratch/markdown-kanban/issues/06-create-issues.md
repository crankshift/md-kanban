# 06: Create issues in an existing feature or effort

Status: ready-for-agent
Blocked by: 05

## Outcome

A user can create an implementation or wayfinding issue in an existing supported container and immediately see it on the appropriate board.

## Scope

- Let the user choose an existing feature/effort and its recognized workflow, then enter the title, initial status, Markdown body, and optional same-scope dependencies.
- Follow the selected container's numbering, filename, title, and metadata conventions. Use the repository's documented numbered Markdown format when no more specific existing style is available.
- Allocate a free number and create the file without overwriting existing work, including when concurrent creation occurs.
- Reuse form validation and editor components where appropriate and show the created issue's details on success.
- Keep creation limited to issues in existing containers; new specifications, efforts, ADRs, custom labels, deletion, and cross-feature dependencies remain outside this issue.

## Acceptance criteria

- Creation works in `.scratch/.../issues`, supported `docs` containers, and a directly selected issue folder with a recognized workflow.
- The created file is compatible with existing discovery and the matching agent ticket conventions.
- Existing issue files cannot be overwritten through number collisions, slugs, or manipulated paths.
- Failed creation keeps the entered content available and does not display an issue as successfully created.
- The board and search include successfully created issues without restarting the app.
- Relevant file/API/form integration checks, type checking, and production build pass.

### Implementation result — 2026-10-06

- Added New issue with a React Hook Form creation flow for existing containers and recognized implementation/wayfinding workflows. Users enter title, initial status, Markdown body, optional dependencies within the same discovered feature/location, and wayfinding Type (default `task`). Preview reuses `SafeMarkdown`. Successful creation inserts the returned persisted issue/revision, clears filters, switches to its workflow, and opens details; board/search work without restarting. Existing editor drafts survive creation, and creation drafts survive closing/navigation, validation errors, stale requests, disk failures, and unconfirmed responses. Explicit Reload containers, keep draft loads a new snapshot for review; discard remains explicit. Before-unload protection covers creation drafts.
- Added `GET /api/creation-targets` and strict Zod-validated `POST /api/create` with `{ container, workflow, expectedRevision, title, status, body, dependencies, type? }`. Creation shares the established local session/Host/Origin/Fetch Metadata protections, 1 MiB request limit, field limits, safe body transforms, and scoped dependency validation. Containers must already contain a valid issue establishing the selected workflow; empty/unsupported folders have no guessed workflow. `.scratch`, supported `docs` containers, and directly selected arbitrary issue folders are covered. The selected creation root is canonicalized once at server startup, and later symlink replacement is rejected.
- Added `src/server/creation.ts` as the separate exclusive creation boundary; existing issue mutations continue through `writer.update`. Loaded container snapshots hash scoped issue revisions/diagnostics, occupied directory names, and directory identities. Creation acquires on-disk `.md-kanban-create.lock` files in sorted discovered scope containers, checks the snapshot, allocates above all occupied/discovered numbers (including malformed files, symlinks, and directories), and rechecks before publication. Overlapping launch roots share locks without placing locks outside the selected root. Concurrent requests from the same snapshot cannot both silently succeed. Content is written/synced to a private temporary sibling and atomically hard-linked to the destination, refusing any existing path rather than overwriting it. Normal failures/success clean up temporary files and owned locks.
- Creation follows the first valid issue in board order for the selected container/workflow: number width (including unpadded numbers), filename separator, numbered/unnumbered heading and number separator, recognized plain/bold metadata keys, LF/CRLF, and final newline when present. Unsupported filename styles fall back to numbered Markdown and a bounded ASCII slug; Unicode titles remain in Markdown. New issues include Status, Blocked by, and wayfinding Type; unknown template metadata/body are not copied. Existing files and unrelated Markdown remain untouched. Heading convention detection uses the first issue H1 so numbered body examples cannot determine the new title style.
- Updated README and contribution guidance for creation, API/file boundaries, lock recovery, allocation/style rules, draft behavior, and verification. No dependency or deferred product feature was added.
