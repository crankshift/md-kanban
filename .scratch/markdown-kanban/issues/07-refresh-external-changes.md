# 07: Refresh external changes while protecting drafts

Status: ready-for-agent
Blocked by: 06

## Outcome

The board stays current as agents edit, create, rename, or remove files, while a user's unsaved work remains recoverable.

## Scope

- Observe selected-root file changes and reconcile the discovered issues with the board, including newly created files and atomically replaced files.
- Refresh untouched issues automatically without resetting search, filters, workflow selection, or unrelated detail state.
- Keep dirty editor drafts when their files change, disappear, or become invalid. Surface conflicts and provide reload or draft recovery rather than silently rebasing or overwriting.
- Integrate successful app writes with external refresh so duplicate notifications do not lose drafts or produce false saved states.
- Clean up watchers and update connections when the server shuts down.

## Acceptance criteria

- Agent-like writes, creations, renames, deletions, and atomic replacements update the board without a process restart.
- Dirty drafts survive external updates/deletions and stale saves remain rejected by the existing write boundary.
- Changes in one issue do not reset another issue's draft or board filters.
- Files becoming malformed move to Needs attention with a diagnostic; supporting documents remain excluded as issues.
- Shutdown releases watcher resources and connections.
- Relevant watcher/server/UI integration checks, type checking, and production build pass.

## Comments

### Implementation result — 2026-10-06

- Added `src/server/watcher.ts`: a recursive `fs.watch` of the selected root whose events are only hints. Bursts are debounced (100 ms), the board is rediscovered, and a SHA-256 fingerprint of it is compared with the last published one, so writes, creations, renames, deletions, atomic temp-file-plus-rename replacements, files becoming malformed, and agent bursts each publish a version, while supporting documents (specs, maps, ADRs), ignored directories, and the app's own `.md-kanban-*` lock/temp files publish nothing. Native watching failure or an unreadable root (a native watcher can die silently when the root is removed or replaced) falls back to polling once per second.
- Added `GET /api/events`, a server-sent event stream (`ready`, `change` with a version) behind the existing Host/Origin/Fetch Metadata checks; it carries no issue data. `startServer` now returns `{ server, url, close }`: `close()` stops the watcher, ends every stream, and closes the server (idempotent); a plain `server.close()` also releases the watcher. The CLI uses `close()` on SIGINT/SIGTERM and exits promptly with a stream open.
- Board refresh (`Board.tsx`): on `ready` (every connection and reconnection) and `change`, the board refetches `/api/issues` and merges it, keeping unchanged issue objects. It never touches search, location/feature filters, the workflow view, the selection, or drafts. It defers to in-flight saves, discards a response that began before a local write or is not the latest request, and replays after the save, so an app write's own notification matches the saved result and cannot show an unsaved state or revert it. Writes still set data from their confirmed response; the write API and the stale-write boundary (`expectedRevision` from the draft's base) are unchanged, so stale editor saves, comments and status/creation requests are still rejected. This ticket adds no new mutation.
- Drafts: the editor stays mounted across external revisions (no lost cursor): without a draft it follows the file; with a draft the form keeps the user's typing and the existing stale-draft banner, **Recover draft on latest version**, and rejection of stale saves apply. The draft list labels drafts whose file changed outside the app or now needs attention. A removed/renamed open issue keeps its panel (`MissingIssue`) with a copyable draft and Discard, and returns in place if the file reappears; a draft whose file returns with different content is a conflict, not a silent rebase. Malformed files move to Needs attention with their diagnostic and the draft stays recoverable. The creation form follows folder changes while untouched; once content is entered it keeps its snapshot, flags the folder as changed, and the server still rejects the stale snapshot until **Reload containers, keep draft**. A **Live** line shows the connection; a dropped connection or failed refresh shows an actionable alert with Reload issues. Unmounting closes the `EventSource`.
- Docs: README (live refresh, draft protection, limitations), CONTRIBUTING (new Refresh boundary section, tests, manual verification steps). No new dependency. Node's `fs.watch` recursive mode (supported on Linux, macOS, and Windows in the required Node 22.12+) and the browser `EventSource` were used from existing knowledge and verified empirically by the tests on this machine (macOS, Node 26); official documentation was not fetched during this run, so the Linux inotify behavior and its limits are untested here. The "events are hints, rediscover and compare" design is deliberately independent of event names and filenames.
- Verification: final `pnpm check` passed strict type checking, the production build, and all 77 tests. New real-filesystem checks: `tests/refresh-events.test.mjs` (event stream and origin protections; write/create/rename/atomic-replace/delete/new-location/malformed; no events for specs/ADRs/guides/ignored folders and one event per burst; one event per app write that matches the saved issue and a stale revision still returns 409; polling fallback; root removal and recreation; shutdown ends streams and releases native watchers via `process.getActiveResourcesInfo`, also for a plain `server.close`; CLI SIGTERM with an open stream) and `tests/live-refresh.test.mjs` (the real React board against a real server through a fetch-based `EventSource`, covering filters/search/workflow/other-issue-drafts preserved, untouched follow without remount, dirty-draft conflicts with rejected stale save/comment and explicit recovery, own saves not duplicated or reverted, a refresh waiting on an in-flight save, removal/reappearance, malformed files and repair, creation snapshots, and disconnection/unmount). The installed-tarball test now observes an external write over the stream and stream closure at shutdown. Tests failed when the editor-follow effect or the in-flight-save guard was removed (mutation spot-checks). `tests/render-board.mjs` now hosts the shared jsdom/real-server renderer used by the board interaction tests. Three consecutive runs of the new files were stable. Portable temporary fixtures and paths only; loopback/package tests ran outside the restricted sandbox as in earlier tickets. No visual-browser check was performed.
- Code review: Standards found no documented breaches or ADR conflicts; I clarified the "only background refresh" wording, removed the unused `debounceMs` option, and deduplicated the board fetch and Reload issues alerts. Spec confirmed the stale-write boundary and refresh/save race handling and raised: the stream cap's 503 would leave `EventSource` permanently closed (removed the unrequested cap); a slow reload response could overwrite a newer one (latest-request guard); a silently dead watcher after root replacement (polling fallback and test); closing an open issue on a transient disappearance (panel now persists); dependency-driven default changes enabling Save without a draft (editor follows defaults); uncancelled creation-target fetches (cancelled on re-run/close). The banner/Reload alerts and the creation-form behaviour are judged part of the "surface conflicts / reload" scope and the ticket 06 handoff. Heartbeats were not added (loopback only).
- Limitations: drafts remain tab memory only, so a draft for a renamed file must be reapplied manually on the new card (no rename inference). Recursive watching of a repository root also watches ignored directories like `node_modules`; large trees can hit OS watch limits and use the 1 s polling fallback. Browsers cap simultaneous connections per local address (about six for HTTP/1.1) and each board tab holds one stream; close extra tabs if one stops responding. An external editor's non-atomic delete-and-recreate may briefly show the issue as removed. Filesystem notification delays on network drives can lag; Reload issues always reads disk. The earlier writer/creation races with external editors that ignore locks remain as documented in tickets 04 and 06. The ~523 kB minified bundle warning remains.
- Handoff for ticket 08: supporting-document browsing is unimplemented. The watcher fingerprint covers discovered issues only and `src/server/watcher.ts` ignores everything in discovery's exported `excluded` set (including `adr` and `assets`); if the document browser should refresh when ADRs/specs change, extend both the fingerprint and that filter, and the client `refreshExternal`/`mergeBoards` path. Reuse `SafeMarkdown`, root-relative path identities, and `tests/render-board.mjs` (`live` option) for UI checks. `MissingIssue`/draft handling is keyed by issue path; document links should not create drafts. Triage remains `ready-for-agent`; only the workflow checkbox records completion.
